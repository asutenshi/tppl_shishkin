1. Обработка больших данных в реальном времени
- Парадигма: императивная
- Язык программирования: C++
- Обоснование:
    - Поток ≈ 3,4 ГБ/с (100 кадров × 4096×4096 × 2 байта) требует высокой производительности и явного контроля над памятью.
    - При 100 кадрах в секунду на обработку одного кадра (32 МБ) есть всего 10 мс. Однопоточная обработка в этот бюджет не укладывается, поэтому работа распределяется между потоками. Условие не уточняет, проверяется ли каждый кадр отдельно или в сравнении с соседними, но параллельная обработка возможна в обоих случаях. Самая тяжёлая часть проверки — проход по 16,7 млн пикселей для подсчёта характеристик кадра (яркость, дисперсия, гистограмма) — зависит только от самого кадра, поэтому разные кадры обрабатываются одновременно в разных потоках. Сравнение этих характеристик с соседними кадрами занимает микросекунды и выполняется последовательно. Если же проверка кадра зависит от результата проверки предыдущего, параллельно обрабатываются части одного кадра (изображение делится на полосы по потокам). Внутри кадра вычисления над пикселями дополнительно ускоряются векторными инструкциями (SIMD).
    - Выявление испорченных кадров — числовые вычисления над массивами данных, что естественно для императивной парадигмы.
    - В C++ нет сборщика мусора. Пауза сборщика даже в 20–50 мс больше бюджета в 10 мс на кадр: входной буфер переполнится и кадры будут потеряны.
    - Для работы 24/7 память выделяется заранее (кольцевой буфер кадров) и не выделяется в цикле обработки, а освобождение ресурсов гарантируется RAII. Так исключаются утечки памяти при длительной работе.
    - Развитая экосистема для обработки изображений и вычислений: OpenCV (обработка изображений), Eigen (линейная алгебра), Intel IPP (оптимизированные функции обработки сигналов), CUDA (вычисления на GPU, если CPU не справится). Все эти библиотеки написаны на C/C++ и используются напрямую, без обёрток.
    - Почему не Rust: Rust тоже не имеет сборщика мусора и дополнительно гарантирует безопасность памяти, но его экосистема для обработки изображений и GPU менее зрелая. OpenCV и CUDA доступны в Rust только через сторонние обёртки над C++-библиотеками, поэтому C++ позволяет использовать проверенные инструменты напрямую.

2. Прототип ML-сервиса для прогноза погодных условий
- Парадигма: Объектно-ориентированная
- Язык программирования: Python
- Обоснование:
    - Быстрый темп разработки (MVP за 2 недели) обеспечивается за счёт:
        - динамической типизации и краткого синтаксиса — меньше кода для той же задачи;
        - готовых пакетов, которые ставятся одной командой `pip install`.
    - Прогноз строится 1 раз в сутки, поэтому не нужен постоянно работающий сервис с низкой задержкой: достаточно скрипта, запускаемого по расписанию (cron). Скорость самих вычислений от Python почти не зависит: NumPy, scikit-learn и PyTorch выполняют тяжёлые операции в скомпилированном коде на C/C++ (и CUDA).
    - Готовые библиотеки покрывают все этапы:
        - pandas, NumPy — загрузка, очистка и агрегация данных с датчиков;
        - scikit-learn — классические модели регрессии (линейная регрессия, случайный лес, градиентный бустинг);
        - statsmodels, Prophet — модели временных рядов;
        - PyTorch — нейросетевые модели, если классических окажется недостаточно;
        - matplotlib — визуализация прогнозов для оценки качества.
    - ООП даёт возможность заменять алгоритмы через общий интерфейс, не трогая остальной код. Например, все модели scikit-learn реализуют одинаковые методы `fit` и `predict`, поэтому замена `RandomForestRegressor` на `GradientBoostingRegressor` — это одна строка, а подготовка данных и оценка качества не меняются.

3. Интерактивный UI для торгового терминала
- Парадигма: Реактивная (обработка потоков данных) + декларативная (описание интерфейса)
- Язык программирования: TypeScript (библиотеки: RxJS для потоков данных, React для отображения)
- Обоснование:
    - Веб-интерфейс, значит нужен язык хорошо работающий в браузере. TypeScript компилируется в JavaScript, который уже выполняется в браузере
    - Статическая типизация TypeScript выявляет ошибки до запуска, например несовпадение формата сообщения из WebSocket с тем, что ожидает виджет. При большом числе виджетов и связей между ними это сокращает количество ошибок, которые иначе пришлось бы ловить тестами
    - Три источника данных + зависимости между 50+ виджетами, значит нужна оперативная реакция на изменения -> реактивная парадигма. WebSocket, REST API и действия пользователя представляются как потоки событий (Observable в RxJS) и объединяются операторами `merge`, `combineLatest`. Каждый виджет подписан на нужный ему поток и обновляется автоматически при изменении источника. Действие в одном виджете — это новое событие в потоке, от которого зависят другие виджеты
    - React сам по себе не реализует реактивную парадигму: он декларативный — интерфейс описывается как функция от состояния, а React сам приводит DOM в соответствие с ним. Поэтому потоки данных обрабатывает RxJS, а React только отображает результат
    - 16 мс — это длительность одного кадра при 60 FPS. React при изменении состояния сравнивает новое дерево виртуального DOM с предыдущим и изменяет в реальном DOM только отличающиеся узлы. Однако сам компонент и всё его поддерево при этом перерисовываются заново, поэтому для 50+ виджетов:
        - состояние хранится отдельно для каждого виджета, чтобы перерисовывался только тот, чьи данные изменились;
        - компоненты оборачиваются в `React.memo`, чтобы не перерисовываться без изменения входных данных;
        - частые обновления из WebSocket (десятки в секунду) прореживаются оператором `throttle` и собираются в одну перерисовку за кадр (`requestAnimationFrame`)
    - Тестируемость достигается отделением логики от отображения:
        - преобразования данных (расчёты, фильтрация, агрегация) — чистые функции без побочных эффектов, они проверяются обычными unit-тестами;
        - потоки RxJS проверяются marble-тестами: `TestScheduler` работает в виртуальном времени, поэтому последовательность событий проверяется без реального сервера и без ожидания;
        - так как интерфейс — функция от состояния, компонент проверяется подачей нужного состояния и проверкой результата через React Testing Library в jsdom, без запуска браузера

4. Прошивка для устройства регистрации температуры
- Парадигма: Императивная, процедурная, с событийно-ориентированной обработкой прерываний
- Язык программирования: C
- Обоснование:
    - 32 КБ RAM и 256 КБ Flash требуют минимального расхода памяти, без лишних абстракций и динамического выделения памяти
    - Низкое энергопотребление достигается тем, что большую часть времени микроконтроллер находится в режиме сна и просыпается только по прерыванию таймера или ADC, делает измерение и снова засыпает. C позволяет управлять этим напрямую: записью в регистры управления питанием и тактированием (отключение неиспользуемой периферии), инструкцией перехода в сон (`__WFI()`), а обработчик прерывания — обычная функция на C. В языках со средой выполнения (сборщик мусора, интерпретатор) фоновые операции будили бы процессор и тратили заряд батареи
    - Язык позволяет напрямую обращаться к регистрам GPIO, ADC, UART через `volatile`-указатели на их адреса и битовые операции
    - Без сборщика мусора и скрытых операций, время выполнения предсказуемо
    - Компиляторы C существуют практически для любой архитектуры микроконтроллеров (ARM Cortex-M, AVR, PIC, MSP430, RISC-V): GCC, Clang, IAR, Keil. Поэтому код на стандартном C (C99/C11) переносится между разными МК
    - Аппаратно-зависимый код выносится в отдельный слой (HAL), остальная логика от МК не зависит. При переходе на другой МК переписывается только этот слой. Для ARM-микроконтроллеров единый интерфейс доступа к ядру дополнительно даёт стандарт CMSIS. Это соответствует процедурной декомпозиции.
